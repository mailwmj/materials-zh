# Elephant 演练

> **Phases 1 and 2**

`elephant` 运行设计对话，然后编写四部分设计文档。它是 EGM 方法的核心：这是设计被创造的地方。

## 它做什么

Elephant 技能假设你已阅读过 `peanuts` 的输出（根 `README.md`），并且你有一个需要设计的功能或组件。它运行一个长、富含上下文的 AI 会话（"the Elephant"），帮助你形成设计，然后将其转化为结构化的设计文档。

设计文档有四部分：

1. **背景** — 我们为什么做这个？它解决什么问题？
2. **需求** — 它必须做什么？成功标准是什么？
3. **设计** — 它如何工作？关键组件、数据结构、接口和流程。
4. **计划** — 我们如何构建它？实施步骤、里程碑和验证方法。

## 何时使用

- 当你有一个需要设计的特性或组件时
- 在 `peanuts` 之后（需要 README 树）
- 在 `goldfish` 之前（需要设计文档供审查）

## 执行步骤

### 步骤 1：设置

1. 创建一个新的 docs/egm/<slug>/ 文件夹
2. 复制 `elephant-ledger-template.md` 到 `docs/egm/<slug>/ELEPHANT.md`
3. 读取根 `README.md` 以了解系统架构
4. 读取 `docs/designs/` 中的任何相关设计文档，以了解现有模式

### 步骤 2：设计对话

与智能体进行设计对话。这是一次长时间的会话，你应该：

- 提出功能需求
- 与智能体讨论架构选择
- 挑战智能体的假设
- 迭代设计，直到你对它感到满意

智能体应主动：
- 提出问题以澄清模糊需求
- 提出替代方案并解释权衡
- 引用 README 中的现有代码以保持一致性

### 步骤 3：编写设计文档

一旦设计稳定，智能体编写四部分设计文档到 `docs/designs/<slug>.md`。

智能体应确保：
- 每个部分都完整且清晰
- 技术选择有理由支持
- 边界情况和失败模式已被考虑
- 文档是独立的（一个新的 AI 会话可以理解它，无需 Elephant 会话的上下文）

### 步骤 4：填充账本

智能体用以下内容填充 `ELEPHANT.md`：
- 设计决策及其理由
- 被考虑但被拒绝的替代方案
- 未解决的问题（供 Goldfish 审查）
- 审查者应关注的关键区域

### 步骤 5：人工审查

人类审查设计文档和账本。检查：
- 设计是否满足需求？
- 技术选择是否合理？
- 文档是否足够清晰，供 Goldfish 审查者理解？

如果设计需要更改，返回步骤 2。

## 输出

- `docs/designs/<slug>.md` — 四部分设计文档
- `docs/egm/<slug>/ELEPHANT.md` — 账本文件，记录设计决策

## 与 Goldfish 的接口

Elephant 的输出是 Goldfish 的输入。Goldfish 技能将读取 `docs/designs/<slug>.md` 并将其发送给三个全新会话进行审查。

这就是为什么设计文档必须是独立的：Goldfish 审查者没有 Elephant 会话的上下文。如果文档依赖于"我们在对话中讨论过"的内容，审查将失败。

## 提示词

`elephant` 使用 `elephant` 提示词来指导智能体进行设计对话。提示词告诉智能体：

- 如何引导设计对话
- 如何提出澄清问题
- 如何记录设计决策
- 如何编写设计文档

## 示例

假设你正在为你的代码库设计一个新的 webhook 重试功能。你启动 `elephant`：

1. 智能体询问：这个 webhook 重试应该多频繁？
2. 你回答：指数退避，最多 3 次尝试。
3. 智能体提出：我们应该使用固定的退避时间还是指数退避？
4. 你回答：指数退避，从 1 秒开始，每次翻倍。
5. 智能体记录决策并继续对话。
6. 经过 20-30 分钟的讨论，设计稳定。
7. 智能体编写四部分设计文档。
8. 你审查文档并签署。

## 限制

- `elephant` 只创建设计文档。它不实施代码、不审查设计、不运行测试。
- 设计对话是迭代的。期望多次往返。
- 设计文档质量取决于对话质量。如果需求模糊，设计也会模糊。
