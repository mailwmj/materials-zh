# elephant

运行一个长时间、富含上下文的设计对话，然后编写四部分设计文档。

## 何时激活

当用户满足以下条件时激活此技能：
- 想要设计一个新功能或组件
- 提到创建设计文档或架构文档
- 需要规划如何构建某物
- 使用诸如"让我们设计"、"我们应该如何构建"、"架构是什么"、"我需要一个设计文档"等短语

当用户想要审查现有代码（使用 mean-review）、从现有设计实施（使用 egm-implement）或引导文档（使用 peanuts）时，不要激活此技能。

## 执行步骤

### 步骤 1：设置

1. 创建一个新的 docs/egm/<slug>/ 文件夹
2. 将 elephant-ledger-template.md 复制到 docs/egm/<slug>/ELEPHANT.md
3. 读取根 README.md 以了解系统架构
4. 读取 docs/designs/ 中的任何相关设计文档，以了解现有模式

### 步骤 2：设计对话

与用户进行长时间、富含上下文的设计对话。这就是"大象"会话。

智能体应该：
- 提出澄清需求的问题
- 提出替代架构并解释权衡
- 引用 README 中的现有代码以保持一致性
- 质疑假设并揭示边缘情况
- 迭代设计，直到双方都满意

人类应该：
- 提供清晰的需求和约束
- 质疑与目标不符的提案
- 在权衡不明确时做出决策
- 确保设计可测试且可实施

### 步骤 3：编写设计文档

一旦设计稳定，就将四部分设计文档写入 docs/designs/<slug>.md。

四个部分是：
1. **背景** — 我们为什么做这个？它解决什么问题？
2. **需求** — 它必须做什么？成功标准是什么？
3. **设计** — 它如何工作？关键组件、数据结构、接口和流程。
4. **计划** — 我们如何构建它？实施步骤、里程碑和验证方法。

智能体应该确保：
- 每个部分都完整且清晰
- 技术选择有理由支持
- 考虑了边缘情况和失败模式
- 文档是自包含的（一个新的 AI 会话可以在没有 Elephant 对话上下文的情况下理解它）

### 步骤 4：填充账本

用以下内容填充 ELEPHANT.md：
- 设计决策及其理由
- 考虑过但被拒绝的替代方案
- 未解决的问题（供 Goldfish 审查）
- 审查者应关注的关键区域

### 步骤 5：人工审查

人类审查设计文档和账本。他们检查：
- 设计是否满足需求？
- 技术选择是否合理？
- 文档是否足够清晰，供 Goldfish 审查者理解？

如果设计需要更改，返回步骤 2。

## 输出

- `docs/designs/<slug>.md` — 四部分设计文档
- `docs/egm/<slug>/ELEPHANT.md` — 记录设计决策的账本文件

## 与 goldfish 的接口

elephant 的输出是 goldfish 的输入。goldfish 技能将读取 docs/designs/<slug>.md 并将其发送给三个全新会话进行审查。

这就是为什么设计文档必须是自包含的：goldfish 审查者没有 Elephant 对话的上下文。如果文档依赖于"我们在对话中讨论过"的内容，审查将失败。
