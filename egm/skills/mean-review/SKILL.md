# mean-review

尽可能严格地审查差异，执行四次脚本强制扫描。

## 何时激活

当用户满足以下条件时激活此技能：
- 想要审查代码更改
- 提到代码审查、PR 审查或质量检查
- 需要查找错误、安全问题或性能问题
- 使用诸如"审查此代码"、"检查我的更改"、"代码审查"、"mean review"等短语

当用户想要设计新功能（使用 elephant）、从设计文档实施（使用 egm-implement）或审查设计文档（使用 goldfish）时，不要激活此技能。

## 执行步骤

### 步骤 1：设置

1. 创建一个新的 docs/egm/<slug>/ 文件夹（如果不存在）
2. 将 mean-review-ledger-template.md 复制到 docs/egm/<slug>/MEAN-REVIEW.md
3. 运行 `git diff` 以获取待审查的更改
4. 读取设计文档（docs/designs/<slug>.md）以了解应该构建的内容
5. 读取 IMPLEMENT.md（如果存在）以了解实施决策

### 步骤 2：运行四次扫描

按顺序运行四次扫描。对于每次扫描：

1. 使用账本模板中的适当提示词审查差异
2. 识别问题并将其分类为：
   - **阻塞** — 继续之前必须修复
   - **严重** — 应该修复，但不阻止发布
   - **警告** — 应该修复，但不紧急
   - **信息** — 值得注意，但不要求修复
3. 将问题记录到 MEAN-REVIEW.md

四次扫描是：
1. **结构扫描** — 代码结构是否合理？模块是否分离良好？命名是否一致？
2. **安全扫描** — 是否有安全漏洞？是否有未验证的输入？是否有硬编码的凭证？
3. **性能扫描** — 是否有性能问题？是否有低效的算法？是否有不必要的计算？
4. **可维护性扫描** — 代码是否易于理解？是否有适当的注释？是否有适当的错误处理？

### 步骤 3：处理阻塞问题

如果有任何阻塞问题：
1. **停止** — 不要继续审查
2. 通知人类存在阻塞问题
3. 人类修复问题
4. 返回步骤 1（重新运行审查）

### 步骤 4：修复和重新运行

对于非阻塞问题：
1. 人类修复问题（或决定跳过）
2. 重新运行审查
3. 返回步骤 2

### 步骤 5：完成

当所有四次扫描通过（无阻塞问题）时：
1. 更新 MEAN-REVIEW.md 以标记审查完成
2. 提交代码（如果适用）
3. 将控制权交还给人类进行最终审查

## 输出

- `docs/egm/<slug>/MEAN-REVIEW.md` — 记录审查发现和修复决策的账本文件

## 设计原则

Mean Review 是"mean"的，因为它被设计为严格的。它不会因为"代码看起来还可以"就通过。它寻找问题，因为它知道人类会跳过它们。

脚本强制执行四次扫描以确保全面性。如果没有脚本，智能体可能会跳过它认为不重要的扫描。脚本确保每次审查都涵盖所有四个维度。

## 扫描规则

### 结构扫描

- 检查模块分离：每个模块是否有一个明确的职责？
- 检查命名：名称是否清晰且一致？
- 检查依赖：依赖是否清晰且最小化？
- 检查接口：接口是否定义良好且使用一致？

### 安全扫描

- 检查输入验证：所有外部输入是否已验证？
- 检查认证：认证和授权是否正确实施？
- 检查加密：敏感数据是否加密？
- 检查凭证：是否有硬编码的凭证或密钥？

### 性能扫描

- 检查算法：算法是否高效？
- 检查数据库查询：查询是否优化？
- 检查缓存：是否有适当的缓存策略？
- 检查资源：资源是否被正确释放？

### 可维护性扫描

- 检查注释：代码是否有足够的注释？
- 检查错误处理：错误是否被适当处理？
- 检查日志：是否有适当的日志记录？
- 检查测试：是否有足够的测试？

## 提示词

`mean-review` 使用 `mean-review` 提示词来指导四次扫描。提示词告诉智能体：

- 每次扫描关注什么
- 如何识别问题
- 如何分类问题
- 如何记录发现

## 脚本

`mean-review` 使用 `enforced_scans.py` 脚本执行四次扫描。脚本：

- 解析 Python 文件（使用 `ast` 和 `tokenize`）
- 对每个文件应用扫描规则
- 将结果输出为待办清单格式
- 标记强制发现（`[enforced]`）和启发式发现（`[heuristic]`）

### 10 行规则

10 行规则是一个可维护性规则：如果一个代码块超过 10 行且没有注释解释为什么，审查者会标记它。

例外：
- 声明式代码（常量、类型别名、Pydantic 模型、路由表）
- 数据定义（结构体、数据类字段列表）

### 弱名称规则

弱名称规则标记没有信息量的名称。审查者报告每个名称每个作用域一次，在首次绑定的行（变量、参数、属性如 `self.data`、函数、类、导入别名）。

`except` 主体被视为引发错误，如果它引发、调用日志记录器上的任何内容，或调用 `print`、`warn`、`exit`、`report` 或类似名称；项目的自己的错误助手需要你的读取。

标记为 `[heuristic]`（其他语言）的发现来自行规则：在报告之前读取 span。

### 声明式代码豁免

常量、类型别名、结构体或数据类字段列表、路由表、模式定义、大型字面量数据：这些是*声明式*的。30 行的功能标志列表或 60 行的 Pydantic 模型不需要每行的*为什么*注释；事物的形状就是解释。仅对非平凡的*逻辑*应用 10 行规则：控制流、转换、IO、状态突变。脚本已经豁免 Python 声明；对于其他语言，放弃它报告的任何声明式 span。如果你标记一个声明式 span，你是错的。

## 限制

- `mean-review` 只审查代码。它不设计功能、不实施代码、不运行测试。
- 扫描是启发式的。它们可能报告误报或错过问题。
- 审查质量取决于智能体对代码的理解。如果代码混乱，审查也会混乱。

## 如果 Python 不可用

如果 Python 不可用，通过阅读和搜索文件手动运行四次扫描，使用相同的规则。
