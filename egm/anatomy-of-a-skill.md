# 一项技能的解剖结构

你已经构建了一个 harness。你了解这个循环：harness **组装** 一个请求，模型 **回答**，harness **应用** 答案。技能是一种将指令放入该循环的方法，而无需在每个请求中为它们付费。本页面展示了如何操作，使用 `skills/` 中的五项 EGM 技能作为示例。

## 技能是什么

一个包含名为 `SKILL.md` 的文件的文件夹。该文件有两个部分：`---` 行之间的 YAML frontmatter，以及一个 markdown 正文。文件夹中的其他任何内容都是可选的。

```
goldfish/
├── SKILL.md                        frontmatter + instructions（必需）
```

## 技能进入循环的位置

Harness 在发送用户消息给模型之前读取 `SKILL.md`。它将 frontmatter 中的描述与用户消息匹配。如果匹配，它将正文附加到系统提示词中。

这意味着技能是**声明式**的：你声明技能何时激活，harness 负责其余部分。

## Frontmatter

Frontmatter 是 `SKILL.md` 顶部的 YAML 块。它有两个字段：

- **name** — 技能的短名称。用于引用技能（如 `/elephant`）。
- **description** — 技能的描述。Harness 使用此描述来确定何时激活技能。

Frontmatter 是可选的，但强烈推荐。没有它，harness 无法知道何时激活技能。

## 描述是触发器

描述是技能最重要的部分。它告诉 harness 何时激活技能。

好的描述：
- 以触发词开头（如"当用户想要..."）
- 具体到可以区分此技能与其他技能
- 包括激活和不应激活的条件

差的描述：
- 泛泛的（如"这是一个有用的技能"）
- 模糊的（如"当用户需要帮助时"）
- 太长的（harness 在匹配描述时使用有限上下文）

## 正文

正文是技能的主要部分。它是 markdown 文本，harness 附加到系统提示词中。

正文应该：
- 按顺序编号步骤
- 每个步骤做一件事
- 指定输入和输出
- 包含分支逻辑（"如果 X，则做 Y"）

正文应该假设智能体知道如何执行基本任务（如写入文件、运行 Git 命令），但不应假设智能体知道领域特定的流程。

## 渐进式披露：参考资料和资产

技能可以包含两个可选的文件夹：

- **assets/** — 模板文件，智能体复制并填充。这些是技能的产物，不是指令。
- **references/** — 上下文文件，智能体在需要时读取。这些不是每次都复制；它们只在智能体需要深入了解时才被加载。

这种分离允许技能保持小巧，同时仍然提供丰富的上下文。

## 脚本

技能可以包含一个 `scripts/` 文件夹，其中包含辅助脚本。这些脚本由技能调用，而不是由智能体直接调用。

脚本应该：
- 是独立的（不依赖外部库，除非已指定）
- 有清晰的输入和输出
- 被记录在技能正文中

## 可移植性

`SKILL.md` 格式是一个开放规范（[agentskills.io](https://agentskills.io/specification)）。Claude Code、Codex、OpenClaw、Gemini CLI、Cursor 和其他许多工具都读取它。

为了最大化可移植性：
- 使用规范中定义的 frontmatter 字段
- 避免 harness 特定的功能
- 测试技能在多个 harness 中

## 测试技能

每个技能应该附带触发测试（`evals/trigger-evals.json`）。这些测试验证描述在应该激活时激活，在不应该激活时不激活。

触发测试有十二个请求：
- 六个应该激活技能（正例）
- 六个不应该激活技能（反例，包括接近 misses）

运行触发测试以确保描述有效。

## 审查问题和练习

1. 选择一个技能并绘制其循环。技能何时激活？它写入什么？下一个技能读取什么？
2. 为你的项目编写一个技能描述。它足够具体吗？它能区分你的技能与其他技能吗？
3. 取一个现有的技能并添加一个参考资料文件。它如何改变智能体的行为？
4. 编写触发测试。你能想出一个会错误激活技能的请求吗？
